# Правила работы OpenCode

## Общие правила

- Отвечай пользователю на русском языке.
- Работай только внутри текущего Git-репозитория и текущей рабочей директории.
- Не изменяй файлы за пределами рабочей директории.
- Не читай, не изменяй и не выводи содержимое `.env`, `.env.local`, `.env.production`, `.env.*` и других файлов с секретами.
- Не выводи API keys, access tokens, private keys, cookies, credentials, пароли и иные чувствительные данные.
- Не удаляй файлы и папки без отдельного подтверждения.
- Не переписывай крупные файлы целиком, если возможно точечное изменение.
- Не добавляй, не удаляй и не обновляй зависимости без объяснения и подтверждения.
- Не выполняй `git reset --hard`, `git clean`, `git push --force`, массовое удаление файлов, публикацию пакетов или релизов без отдельного подтверждения.
- Не меняй конфигурацию деплоя, GitHub Pages, GitHub Actions, CI/CD, production-настройки и секреты без отдельного подтверждения.
- Не изменяй несвязанные с задачей файлы.
- Сохраняй существующую архитектуру, публичные интерфейсы, соглашения по коду и стиль проекта.
- Используй строгий TypeScript. Не добавляй `any` без необходимости и объяснения.

## Git-режим по умолчанию

### Главное правило

**Перед любым изменением кода, конфигурации, зависимостей, документации или тестов агент обязан работать в отдельной экспериментальной ветке `ai/...`.**

Не начинай изменения прямо в `main` или `master`, даже если пользователь явно не упомянул ветки.

### Перед началом работы

Перед изменениями всегда выполни:

```bash
git status
git branch --show-current
git fetch origin
```

Дальше действуй так:

1. Если есть незакоммиченные изменения, не принадлежащие текущей задаче, остановись и сообщи пользователю.
2. Если текущая ветка — `main` или `master`, создай и переключись на новую ветку:
   ```bash
   git switch -c ai/<тип>-<краткое-название-задачи>
   ```
3. Если текущая ветка уже начинается с `ai/`, продолжай работу в ней только если она относится к текущей задаче.
4. Если текущая ветка не `main`, `master` и не `ai/...`, спроси пользователя, нужно ли продолжать в ней или создать новую `ai/...` ветку.
5. Перед первым изменением явно сообщи пользователю текущую ветку и название созданной экспериментальной ветки.

Используй имена веток:

```text
ai/feature-<name>
ai/fix-<name>
ai/refactor-<name>
ai/docs-<name>
ai/chore-<name>
```

Пример:

```bash
git switch -c ai/feature-profile-page
```

### Явное разрешение на работу в main

Если пользователь прямо просит один из вариантов:

```text
Работай прямо в main.
Вноси изменения в main.
Не создавай экспериментальную ветку.
Не переходи в ai-ветку.
Делай изменения сразу в основной ветке.
```

то разрешено работать непосредственно в `main` или `master`.

В этом случае:

1. Сообщи пользователю, что изменения будут внесены сразу в основную ветку.
2. Выполни:
   ```bash
   git status
   git branch --show-current
   git fetch origin
   ```
3. Убедись, что текущая ветка действительно `main` или `master`.
4. Если есть незакоммиченные изменения, остановись и сообщи пользователю.
5. Не создавай экспериментальную ветку.
6. Не выполняй `git push origin main`, `git push origin master`, merge, rebase, публикацию или деплой без отдельного подтверждения пользователя.
7. До критических действий покажи краткий итог изменений, результаты проверок и список коммитов, которые будут опубликованы.

### После выполнения задачи в ai-ветке

После реализации и проверок:

1. Добавь в staging только файлы текущей задачи:
   ```bash
   git add <список-файлов>
   ```
2. Создай понятный коммит:
   ```bash
   git commit -m "<type>: <краткое описание>"
   ```
3. Запушь текущую экспериментальную ветку:
   ```bash
   git push -u origin HEAD
   ```
4. Сообщи пользователю:
   - имя ветки;
   - hash последнего коммита;
   - изменённые файлы;
   - результаты проверок;
   - что ветка готова к созданию Pull Request.
5. Не создавай Pull Request, не переключайся на `main` и не выполняй merge без прямого указания пользователя.

### Когда пользователь говорит, что всё нормально

Если пользователь сообщает, например:

```text
Всё нормально.
Можно принимать изменения.
Можно в main.
Подготовь PR.
Создавай Pull Request.
```

то:

1. Проверь, что текущая ветка начинается с `ai/`.
2. Покажи:
   ```bash
   git status
   git log -1 --oneline
   git diff origin/main...HEAD --stat
   ```
3. Запусти финальные проверки, если после последнего запуска были новые изменения:
   ```bash
   npm run lint
   npx tsc --noEmit
   npm run build
   ```
4. Создай Pull Request из текущей `ai/...` ветки в `main`.
5. Покажи пользователю ссылку на Pull Request и краткое описание.
6. Не мержи Pull Request и не пушь изменения в `main`, пока пользователь отдельно и явно не подтвердит merge.

Если пользователь явно пишет:

```text
Мержи PR в main.
Подтверждаю merge в main.
Вливай изменения в main.
```

то перед merge:

1. Покажи ветку-источник, ветку-назначение и последний commit.
2. Покажи краткий diff и результаты проверок.
3. Запроси подтверждение на критическое действие: merge и публикацию в `main`.
4. Только после подтверждения выполни merge через Pull Request или локально.
5. После успешного merge сообщи commit SHA и статус GitHub Pages/deploy, если он запустился.

## Порядок работы с задачей

### Этап анализа

Не начинай сразу с изменения файлов, если задача затрагивает несколько компонентов, API, авторизацию, базу данных, интеграции или архитектуру проекта.

Перед изменениями:

1. Изучи структуру проекта.
2. Найди связанные компоненты, страницы, типы, API routes, middleware и конфигурационные файлы.
3. Определи текущий поток данных.
4. Перечисли файлы, которые потребуется изменить.
5. Составь краткий пошаговый план.
6. Для крупной или неоднозначной задачи ничего не изменяй до отдельного подтверждения пользователя.

Если задача недостаточно понятна, задай уточняющий вопрос, а не делай предположения.

Для небольшой, однозначной и безопасной задачи можно пропустить ожидание подтверждения плана, но сначала всё равно создай или переключись в ветку `ai/...`, если пользователь явно не разрешил работу в `main`.

### Этап реализации

После подтверждения плана или для небольшой однозначной задачи:

1. Убедись, что работа идёт в ветке `ai/...`, если пользователь явно не попросил работать прямо в `main`.
2. Реализуй только согласованный план.
3. Вноси изменения небольшими логическими шагами.
4. Не изменяй `.env`-файлы, секреты, CI/CD, GitHub Pages и несвязанные файлы.
5. Не добавляй новые зависимости без объяснения и отдельного подтверждения.
6. Не выполняй push в `main` или `master`.
7. Не выполняй merge, rebase, `git reset --hard`, `git clean`, массовое удаление или публикацию без отдельного подтверждения.
8. Перед потенциально опасной операцией остановись и запроси подтверждение.
9. Если проверки обнаружили ошибки, исправляй только ошибки, вызванные или затронутые текущей задачей.

### Проверка результата

После изменений:

1. Покажи список изменённых, созданных и удалённых файлов.
2. Кратко опиши изменения по каждому файлу.
3. Покажи потенциальные побочные эффекты и известные ограничения.
4. Проверь доступные команды в `package.json`.
5. Запусти подходящие проверки:
   ```bash
   npm run lint
   npx tsc --noEmit
   npm run build
   ```
6. Если команда отсутствует, не угадывай: сообщи об этом пользователю.
7. В конце покажи результаты всех команд.
8. Создай commit и push в текущую `ai/...` ветку автоматически, если пользователь не запретил это в конкретной задаче.
9. Не создавай Pull Request, не выполняй merge и не пушь в `main` без прямого указания пользователя.

## Безопасная формулировка задач

### Формат первоначального промпта

Если пользователь просит реализовать новую функцию, сначала предложи ему такой формат:

```text
Сначала только проанализируй проект. Ничего не изменяй.

Задача: [описание задачи]

Определи:
1. какие файлы связаны с этой задачей;
2. как сейчас устроен соответствующий поток данных;
3. какие существующие компоненты, типы и API можно переиспользовать;
4. какие файлы потребуется изменить;
5. какие риски и побочные эффекты возможны.

После анализа остановись и покажи план реализации.
```

### Формат реализации после подтверждения

После подтверждения плана работай по следующему формату:

```text
Реализуй только согласованный план.

Сначала проверь Git-статус и текущую ветку.
Если я явно не разрешил работу в main, создай или используй ветку ai/... для этой задачи.

Ограничения:
- не трогай `.env`-файлы и секреты;
- не добавляй зависимости без согласования;
- не изменяй несвязанные файлы;
- после изменений запусти `npm run lint` и `npx tsc --noEmit`;
- создай commit и запушь только ветку `ai/...`;
- не создавай PR, не мержи и не пушь в main без моего прямого указания.

В конце покажи:
1. имя ветки и hash коммита;
2. список изменённых файлов;
3. краткое описание изменений;
4. результаты проверок;
5. оставшиеся проблемы или предупреждения.
```

## Отчёт об изменениях агента

После завершения каждой задачи обязательно создай или обнови файл:

```text
.agent/CHANGELOG.md
```

Этот файл предназначен для пользователя и должен вестись на русском языке.

### Правила обновления

- Создавай новую запись в начале файла, не удаляя историю предыдущих задач.
- Перед созданием коммита обнови `.agent/CHANGELOG.md`.
- Добавляй `.agent/CHANGELOG.md` в тот же коммит, что и изменения задачи.
- Не записывай в отчёт секреты, API keys, токены, содержимое `.env` и приватные данные.
- Не включай в отчёт большие фрагменты исходного кода.
- Если задача была только аналитической и код не менялся, всё равно добавь запись с пометкой «Изменений в коде нет».

### Формат записи

Используй следующий шаблон:

```md
## YYYY-MM-DD — <краткое название задачи>

**Ветка:** `ai/<название-ветки>`  
**Коммит:** `<короткий SHA или "ещё не создан">`  
**Статус:** `готово` / `частично готово` / `нужна проверка`

### Что сделано

- Краткое действие 1
- Краткое действие 2

### Изменённые файлы

- `src/path/file.ts` — что изменено
- `src/path/component.tsx` — что изменено
- `package.json` — изменение зависимостей, если оно было

### Проверки

- `npm run lint` — успешно / ошибка: краткое описание
- `npx tsc --noEmit` — успешно / ошибка: краткое описание
- `npm run build` — успешно / не запускалось / ошибка: краткое описание
- Тесты — успешно / не запускались / ошибка: краткое описание

### Требует внимания

- Нет
```

Если есть риск, незавершённая часть работы, ручная настройка или потенциальная регрессия — агент обязан перечислить это в разделе «Требует внимания».
